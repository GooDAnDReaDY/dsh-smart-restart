# DESIGN — dsh-smart-restart

## 1. Задача

Перезапуск харнесса перестаёт быть операцией «на честном слове»: агент просит перезапуск, а плагин
после старта **проверяет**, что всё поднялось, **сообщает** вердикт в ту сессию, которая просила, и
возвращает **намерение** «что продолжить».

## 2. Границы

**Входит:** перезапуск без привилегий (kill + `Restart=always`), health-check после старта,
отчёт в сессию, файл-намерение, защита от петли, карточка настроек.

**Не входит:** управление другими сервисами, sudo/polkit-настройка, canary-инстансы, автопочинка
чужих плагинов; перезапуск при потере питания; Windows-специфика.

## 3. Пользовательские сценарии

| # | Сценарий | Что видит владелец/агент |
|---|---|---|
| 1 | Агент меняет конфигурацию и просит перезапуск | Инструмент возвращает квитанцию, процесс завершается, systemd поднимает сервис |
| 2 | Проверка после старта | В сессию приходит отчёт: время старта, простой, вердикт по пунктам, «продолжи: …» |
| 3 | Что-то не поднялось | Вердикт `degraded` со списком провалившихся проверок, а не молчание |
| 4 | Перезапуск по кругу | Четвёртый перезапуск за 10 минут отклоняется с объяснением |

## 4. Поверхности

- **Инструменты** `dsh_restart` и `dsh_restart_status`.
- **Карточка настроек** в списке плагинов (`plugins.item` + `settings.plugin.item`).
- **Сообщение в сессию** — основной пользовательский результат: отчёт после перезапуска.

## 5. Контракт инструментов

- `dsh_restart` требует `confirm: true` (или `dryRun: true`); принимает `reason`, `resume`, `delayMs`, `dryRun`; возвращает
  `{ ok, restarting, delayMs, mode, boot, preflight, drain }` либо отказ с причиной (петля, нет юнита, выключено, отказ предполётной проверки).
- `dsh_restart_status` — только чтение: `{ lastBoot, downtimeMs, restartsInWindow, pendingIntent,
  lastReport }`.
- Значение результата обязано переживать JSON без потерь (никаких `undefined`).

## 6. Состояния

`ok` — все проверки прошли; `degraded` — часть проверок провалилась (список в отчёте);
`disabled` — плагин выключен настройкой; `no-unit` — юнит не найден; `loop-guard` — отказ по
счётчику; `stale-intent` — намерение старше TTL, в отчёт попадает с пометкой;
`preflight-failed` — отказ предполётной проверки с отправкой причины в сессию.

## 7. Данные и безопасность

- Состояние: `$DSH_HOME/.restart-guard/{marker.json,intent.json,last-report.json,history.json}`;
  намерение содержит id сессии, причину, текст «что продолжить» и статистику дренажа — секретов там быть не должно.
- Перезапуск по умолчанию не требует прав; режим `systemctl` используется только там, где права
  уже выданы.
- Отчёт не содержит путей, адресов и идентификаторов инфраструктуры за пределами юнита и порта.

## 8. Приёмка

| Проверка | Критерий |
|---|---|
| Тесты | `npm test` без сети и харнесса, зелёный |
| Preflight | без FAIL |
| Тестовый сервер | установка, перезапуск, отчёт в сессию, cleanup |
| Прод | тот же `.tgz`, затем registry-версия; отчёт после перезапуска |
| Интерфейс | карточка: заголовок, раскрытие, сохранение; en + zh |

## 9. Обновление (Updater)

Плагин является модулем web-профиля DeepSeek Harness и управляется штатным пакетным
менеджером DSH (`dsh plugin add / update` или `pnpm`). Плагин намеренно не регистрирует
автономного HTTP-роута `/api/dsh/update` и не выполняет бинарную автозамену: обновление
доставляется через пакетный менеджер, а факт успешного старта и совместимости после
обновления проверяется встроенным health-check при перезапуске.

## 10. Жизненный цикл (Cordis 4 Lifecycle)

Все фоновые таймеры (пауза перед проверкой бута, задержка перед сигналом рестарта, повторные
попытки доставки в сессию) и регистрация инструментов привязаны к `ctx.effect`. При
выгрузке или перезагрузке плагина активные таймеры немедленно очищаются, исключая
утечки памяти, дублирование проверок и ложные срабатывания loop-guard.

## 11. Поддержка systemd user units

Для сервисов, запущенных в пространстве пользователя (`/user.slice/`), команда
`systemctl restart` автоматически дополняется флагом `--user`, аналогично проверке
`checkUnit` (`systemctl --user show`).

## 12. Контракт настроек DSH 0.2.0 (Unwrap → Validate → Unwrap)

Поля схемы конфигурации Config объявлены как .volatile(), чтобы карточка настроек
в DSH 0.2.0 обслуживалась ядром через динамические формы ConfigForm.
При вызове apply(ctx, rawConfig) входящий объект конфигурации может содержать боксы Volatile,
поэтому применяется строгая последовательность:
1. plainConfig(rawConfig) распаковывает входящие боксы в плоские значения;
2. Config(...) валидирует значения по схеме;
3. plainConfig(...) разворачивает результат в validatedConfig.
Динамическое чтение через live() производит plainConfig(entryConfig) на каждый запрос,
отслеживая обновления формы Loader в реальном времени.
Слот карточки в Plugin Manager регистрируется под единым хостовым namespace goodandready-smart-restart
(id: NS для plugins.item и key: NS для plugins.row.config).

## 13. Защита выполнения и хостовый примитив подтверждения (Host Approval Primitive)

1. **Хостовый примитив подтверждения (`requireApproval`)**:
   Инструмент `dsh_restart` больше не считает аргумент `{ confirm: true }` от LLM достаточным основанием для перезапуска сервиса или отправки `SIGTERM`. По умолчанию включён параметр `requireApproval: true`. Плагин регистрирует перехватчик `tools/pre-execute` waterfall с высоким приоритетом (`prepend: true`), возвращающий `{ kind: 'ask', reason: ... }`. При выполнении инструмента дополнительно проверяется хостовый сервис подтверждений через `ctx.approval.request(...)`. При отказе или отсутствии подтверждения вызов завершается ошибкой `Restart cancelled: authorization denied`.
2. **Синтаксическая и адресная валидация systemd unit**:
   Имя сервиса проверяется строгим регулярным выражением `^[A-Za-z0-9@_.-]+\.service$`. При генерации команды `systemctl restart` проверяется соответствие переданного имени юниту, обнаруженному в контрольной группе (`/proc/self/cgroup`), исключая перезапуск сторонних системных служб.
3. **Защита от выхода за пределы каталога (Path Traversal Guard)**:
   Путь `stateDir` нормализуется с помощью `resolveSafeStateDir()`. Любые попытки выхода через `../` за пределы `$DSH_HOME` блокируются, и путь принудительно возвращается к безопасному каталогу по умолчанию `$DSH_HOME/.restart-guard`.
4. **Защита от переполнения 32-битного таймера Node.js**:
   Задержка перезапуска `delayMs` валидируется и ограничивается функцией `clampDelayMs()` в диапазоне от `500` мс до `2147483647` мс (максимум для signed 32-bit int), исключая сброс таймера в `1` мс при значениях больше `2^31 - 1`.
5. **Семантика доставки `target: 'primary'`**:
   В ядре DSH отсутствует отдельная сущность «primary». Семантика `target: 'primary'` формализована как доставка первому активному интерактивному корню агентов `ctx.agents.roots()[0]` с безопасным резервным переходом к первому зарегистрированному агенту `ctx.agents.list()[0]`.

## 14. Предполётная валидация и безопасный дренаж активных задач (Pre-flight & Graceful Drain)

1. **Предполётная проверка конфигурации и среды перед перезапуском (#38)**:
   - Перед инициированием перезапуска сервис выполняет проверку `validateRestartPreflight()`:
     - Синтаксическая валидация `package.json` (`JSON.parse`).
     - Синтаксическая валидация файлов конфигурации Cordis (`cordis.patch.yml`, `cordis.yml`) на отсутствие запрещённых спецификацией YAML табуляций для отступов и баланс скобок (`validateYamlSyntax`).
     - Проверка корректности формата системного юнита (`UNIT_NAME_PATTERN`).
     - Проверка отсутствия посторонних процессов, удерживающих сетевые порты службы (`checkPort`).
   - При обнаружении ошибок валидации перезапуск отменяется (`ok: false`), а в сессию вызывающего агента немедленно отправляется форматированное уведомление с деталями отказа (`formatPreflightFailureReport`).
   - Поддерживается режим симуляции `dryRun: true`: валидация выполняется полностью без завершения процесса и без создания `intent.json`.

2. **Защита активных задач от обрыва (Graceful Drain, #39)**:
   - Перед отправкой сигнала `SIGTERM` или вызовом `systemctl` плагин инспектирует активных агентов в `ctx.agents.list() / ctx.agents.roots()` с помощью `countActiveAgents(agents, callerSessionId)`.
   - Сессия самого инициатора исключается из ожидания, предотвращая взаимную блокировку.
   - Плагин ожидает завершения активных задач других агентов в течение `drainTimeoutMs` (по умолчанию `15000` мс, настраивается в конфигурации и карточке WebUI).
   - Статистика дренажа (`drained`, `waitedMs`, `activeCount`) фиксируется в файле `intent.json` и возвращается в ответе инструмента.

## 15. Ситуационный снимок контекста и атрибуция диффа пакетов (Situational Snapshot & Diff Attribution)

1. **Ситуационный снимок рабочего контекста (`context`, #40)**:
   - Инструмент `dsh_restart` принимает опциональный структурированный объект `context`, фиксирующий активное состояние сессии перед перезагрузкой:
     - `cwd`: рабочая директория (если не указана явно, автоматически подставляется `process.cwd()`);
     - `branch`: текущая git-ветка;
     - `worktree`: имя или путь рабочего дерева;
     - `files`: список файлов, с которыми велась работа (`string[]`);
     - `tasks`: список запланированных или выполняемых задач (`string[]`);
     - `memoryTag`: тег долговременной памяти для восстановления контекста;
     - произвольные дополнительные параметры сохраняются без искажения.
   - Данные контекста сохраняются в `intent.json` и защищены от потери при перезапуске.
   - В отчёте после загрузки контекст форматируется в строку `- context: branch: ..., cwd: ..., files: [...], tasks: [...]`.
   - Если параметр `resume` не был передан явно, но предоставлен `context`, отчёт автоматически формирует директиву `resume: carry on with the saved context.`
   - Данные контекста доступны для чтения агентами через инструмент `dsh_restart_status` (`pendingIntent.context` / `lastReport.context`).

2. **Атрибуция диффа установленных пакетов (`packages`, #41)**:
   - При старте плагин инвентаризирует зависимости (`dependencies` и `devDependencies` из `profiles/web/package.json` или `package.json`) и фиксирует их в маркере загрузки `marker.json` (`packages`).
   - Функция `diffPackages(previous, current)` вычисляет изменения с момента предыдущего маркера:
     - `changed`: список изменённых пакетов (`name`, `from`, `to`);
     - `added`: список вновь установленных пакетов (`name`, `version`);
     - `removed`: список удалённых пакетов (`name`, `version`);
     - `hasChanges`: флаг наличия фактических изменений.
   - При первой «холодной» загрузке или отсутствии предыдущего маркера дифф не генерирует ложных срабатываний (`hasChanges: false`).
   - При обнаружении изменений дифф форматируется функцией `formatPackageDiff()` в компактную строку (например, `core-pkg 0.1.0 -> 0.2.0, + lodash@4.17.21, - left-pad@1.0.0`) и включается в отчёт агенту (`- changes: ...`).
   - Структурированный дифф сохраняется в `last-report.json` (`diff`) и предоставляется через инструмент `dsh_restart_status.lastDiff`.

## 16. Интерактивный дашборд надёжности и отмена перезапуска в WebUI (Dashboard & Grace Period UI)

1. **Интерактивный дашборд надёжности в карточке настроек WebUI (`RestartGuardCard`, #42)**:
   - В карточку настроек встроен интерактивный дашборд здоровья и надёжности сервиса:
     - Бейдж статуса здоровья (`Healthy`, `Degraded`, `Loop guard active`) с семантической подсветкой через CSS-переменные DSH без хардкода цветов.
     - Бейджи индивидуальных проверок (статус портов, systemd unit, службы ядра, версии плагина и ядра).
     - Компактная таблица недавних перезапусков (`Recent restarts`) с отображением времени перезапуска, даунтайма (`downtimeMs`) и причины.
     - Действие «Безопасный перезапуск» (`Safe restart`): запускает предполётную валидацию с настраиваемой задержкой (grace period) и модальным подтверждением оператора.
   - Данные статуса запрашиваются через маршрут `GET /dsh-smart-restart/status`.

2. **Всплывающий баннер обратного отсчёта и экстренная отмена (Grace Period UI, #43)**:
   - При инициировании перезапуска с задержкой (агентом или через WebUI) в интерфейсе появляется баннер обратного отсчёта:
     - Отображение оставшегося времени в секундах (`Restarting in X seconds...`) и причины перезапуска.
     - Кнопка экстренной отмены `[Cancel restart]`.
   - Нажатие кнопки вызывает защищённый эндпоинт `POST /dsh-smart-restart/cancel` (также доступный агентам через инструмент `dsh_restart_cancel`):
     - Немедленно очищает активный таймер перезапуска.
     - Удаляет файл намерения `intent.json`.
     - Оповещает вызывающую сессию об отмене запланированного перезапуска.
     - Защита write-маршрутов включает проверку источника (CSRF / peer validation через `isTrustedRequest`: `sec-fetch-site`, `origin`, `remoteAddress`).


## 17. Чат-команда прямого перезапуска и перехватчик сообщений без SSH (Chat Command, #44)

1. **Чат-команда `/restart` (и алиасы `!restart`, `/dsh-restart`)**:
   - Позволяет оператору и разработчику перезагрузить DeepSeek Harness текстовой командой прямо из интерфейса диалога без терминала и SSH-сессии.
   - Двухуровневая интеграция:
     - Регистрация в реестре `@deepseek-ai/dsh-commands` (`commands.register({ name: 'restart', ... })`) для нативного автодополнения в клиенте;
     - Защитный текстовый перехватчик `ctx.middleware(async (session, next) => ...)`, обрабатывающий сообщения, начинающиеся с `/restart`, `!restart`, `/cancel-restart`, даже если сервис команд не загружен, с прерыванием передачи сообщения LLM (без расхода контекста и токенов).
   - Поддерживаемые команды и параметры:
     - `/restart` — запрос на безопасный перезапуск с автоматическим запуском preflight-проверок;
     - `/restart --confirm` (или `-y`) — пропуск подтверждения при включённом `requireApproval`;
     - `/restart --dry-run` (или `-n`) — проверка конфигурации и среды без фактического перезапуска;
     - `/restart --delay=<duration>` (или `-d 10s`) — задание интервала задержки (grace period, по умолчанию 5s для чата);
     - `/restart --reason="<text>"` (или `-r "..."`, либо произвольный позиционный текст) — указание причины перезапуска;
     - `/restart cancel` (или `/cancel-restart`) — экстренная отмена запланированного перезапуска;
     - `/restart status` — мгновенная сводка о здоровье, портах, лимитах перезапуска и запланированных операциях.
2. **Конвейер выполнения и фиксация диалога**:
   - Текущая сессия чата автоматически распознаётся (`sessionIdOf(session)`) и фиксируется в `intent.json` (`sessionId`, `source: 'chat-command'`).
   - Перед перезапуском выполняется валидация `validateRestartPreflight`: в случае ошибок они сразу возвращаются в чат в понятном виде, предотвращая поломку сервиса.
   - Защита от частых перезапусков (`loopGuard`) проверяет бюджет перезапусков в плавающем окне.
   - При завершении перезапуска система уведомлений направляет отчёт с вердиктом здоровья (`verdict`), диффом пакетов (`changes`) и сохранённым контекстом обратно в этот же диалог.
